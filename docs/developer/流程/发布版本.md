# 版本发布流程

> 本文面向脚本维护者，规定从确定版本内容到线上发布、自测和回滚的完整流程。除非发布目标明确要求，否则不得跳过版本核对、公告审核、测试或产物校验。

---

## 一、发布原则

### 1. 更新公告面向谁

更新公告只面向从上一个正式版本升级的普通玩家，回答三件事：

- 升级后新增了什么可使用的功能。
- 原有功能有哪些玩家能够感知的变化。
- 玩家需要注意哪些开关、风险或配置变化。

公告不是开发日志、测试报告或写给作者的工作总结。不得写入仅在本版本开发过程中出现、且发布前已经修好的临时问题。

### 2. 比较基准

每次公告必须以上一个正式发布版本为基准，只描述新版本相对旧版本的最终差异。

开始写公告前必须先读取旧版本内嵌的 `UPDATE_NOTES`、旧版正式产物或可靠的版本记录，确认哪些功能旧版已经存在。不能把旧版已有功能再次写成“新增”，也不能因为本次重构了内部实现就对外宣称新增功能。

### 3. 修改源文件，不直接修改构建产物

- 版本、公告、界面文字和功能代码一律修改 `src/arcane-assistant-v2.1.3.base.js` 或 `src/constants.js`。
- `dist/奥术摸鱼大师辅助.user.js` 只能由 `npm run build` 生成。
- 不得直接编辑 `dist` 后跳过构建，否则下次构建会覆盖修改。

### 4. 本地准备与线上发布分开

- “准备发布包”默认只包括本地改版、测试、构建和校验。
- 上传脚本、修改线上 `/opt/asmy/latest_version.txt`、替换服务端程序或重启服务属于线上发布动作，必须得到明确授权后执行。
- 本地 `server/latest_version.txt` 可以随版本准备同步更新，但它不代表线上已经发布。

---

## 二、版本号规则

正式版本使用 `主版本.次版本.修订号`，例如 `1.9.0`。

- 主版本：存在重大不兼容变化时提升。
- 次版本：新增明显功能或较大范围体验升级时提升。
- 修订号：只包含兼容性修复或小幅优化时提升。

以下位置必须保持一致：

| 位置 | 文件 | 用途 |
|---|---|---|
| `@version` | `src/arcane-assistant-v2.1.3.base.js` | 油猴等脚本管理器识别版本 |
| `SCRIPT_VERSION` | `src/constants.js` | 更新弹窗、版本比较和数据上报 |
| 包版本 | `package.json`、`package-lock.json` | 本地测试与构建标识 |
| 最新版本文件 | `server/latest_version.txt` | 本地服务端版本接口配置 |

构建后还必须检查 `dist/奥术摸鱼大师辅助.user.js` 中的 `@version` 和 `SCRIPT_VERSION` 是否一致。

## 三、更新公告规则

### 1. 公告存放位置

正式更新公告只写入 `src/constants.js` 的 `UPDATE_NOTES`，由脚本在玩家首次载入新版本时弹出一次。

除非明确要求制作群公告或论坛帖子，不额外创建独立的当版公告文件。需要对外复制时，应以 `UPDATE_NOTES` 为唯一内容来源，避免出现两个版本。文档站的“更新历史”只在版本正式发布后归档已经发布的公告，不参与定义当版发布内容。

### 2. 固定格式

沿用现有脚本公告风格，按实际内容使用以下分段，顺序固定：

```js
export const UPDATE_NOTES = '【新增】\n\n- 一句话说明\n\n【修复】\n\n- 一句话说明\n\n【优化】\n\n- 一句话说明\n\n【移除】\n\n- 一句话说明';
```

没有内容的分段直接省略，不得为了凑齐格式填写“无”。固定采用 `新增 → 修复 → 优化 → 移除`，分类标题与第一条内容之间保留一个空行。

如当版需要展示赞助说明，赞助内容必须直接写在同一个 `UPDATE_NOTES` 的全部版本内容之后，使用 `**支持开发**` 作为标题；不得置顶，不得另建当版公告或独立模板文件。赞助必须明确为完全自愿，不影响脚本功能、更新、工单回复、问题反馈或功能优先级。

### 3. 各分段判定

- `【新增】`：旧正式版没有、玩家升级后可以直接使用的新功能或新配置。
- `【优化】`：旧功能仍然存在，但操作方式、提示、安全性、性能或结果更好。
- `【修复】`：上一个正式版中真实存在、玩家可能遇到的问题，并且本版本已经修复。
- `【移除】`：旧功能、旧配置或兼容入口被删除，且玩家需要知道。

### 4. 禁止写入的内容

- 本版本开发过程中发现并在发布前修掉的临时 bug。
- 单元测试场景、测试数量、内部函数名或文件名。
- `幂等键`、`并发锁`、缓存签名等纯技术词；优先改写成“不会重复提交”“以服务端记录为准”等结果描述。
- “根据你的要求”“已为你实现”等面向作者的措辞。
- 无法从代码、测试或旧版产物确认的功能与修复。
- 为显得内容多而拆分的重复条目。

### 5. 文风要求

- 使用玩家能够理解的功能名称和界面文字。
- 每条先写结果，再补充必要的触发条件、默认值或限制。
- 同类设置尽量合并成一条，长度和信息密度参考上一版内嵌公告。
- 明确重要默认值，例如“默认关闭”“普通到稀有默认开启”。
- 测试功能必须说明仍在测试阶段、建议开启调试日志、异常时如何关闭和反馈。
- 公告中的功能名称、按钮名称和百分比必须与实际界面一致。

### 6. 公告审核问题

写完后逐条回答：

1. 这项内容在上一个正式版本中是否已经存在？
2. 玩家升级后是否能直接感知这项变化？
3. 这是正式版遗留问题，还是本次开发中的临时问题？
4. 玩家是否看得懂，是否必须知道这条信息？
5. 描述的默认值、开关状态和限制是否与代码一致？

任一条无法确认，就先查代码和旧版记录，不得猜测。

## 四、本地发布流程

### 第一步：确定版本范围

1. 明确上一个正式版本和目标版本。
2. 汇总最终保留的玩家可见变化。
3. 区分新增、优化、正式版 bug 修复和内部开发修正。
4. 确认是否涉及服务端、数据结构、配置迁移或文档变化。

### 第二步：更新版本号

同步修改：

- `src/arcane-assistant-v2.1.3.base.js` 的 `@version`。
- `src/constants.js` 的 `SCRIPT_VERSION`。
- `package.json` 和 `package-lock.json` 的包版本。
- `server/latest_version.txt` 的本地最新版本号。

同时检查 `@description` 是否需要补充新增的主要功能，但不要堆砌实现细节。

### 第三步：重写内嵌公告

1. 读取上一正式版公告作为内容基准和文风参考。
2. 按本文件“更新公告规则”编写 `UPDATE_NOTES`。
3. 删除开发日志式、重复或玩家不可感知的条目。
4. 核对公告中的默认值、开关名称和功能状态。
5. 如包含赞助说明，确认其位于所有“新增、修复、优化、移除”内容之后，且仍由同一个 `UPDATE_NOTES` 提供。

### 第四步：同步必要文档

仅更新受本版本实际影响的长期文档，例如：

- 功能用法变化：更新 [功能指南](../../user/功能指南.md) 或对应 FAQ。
- API 或数据源变化：更新 [浏览器脚本 API](../../reference/浏览器脚本API.md)、[数据源](../../reference/数据源.md) 或对应专题参考。
- 发布规则变化：更新本文。

不要仅为保存一份与 `UPDATE_NOTES` 重复的内容而创建版本公告文件。

如果维护者另行部署文档站，可在版本正式发布并完成线上验证后，将当版 `UPDATE_NOTES` 归档到文档站的“更新历史”页面：

1. 新版本插入在旧版本上方；
2. 标题统一使用 `## v主版本.次版本.修订号`；
3. 分类固定按“新增 → 修复 → 优化 → 移除”排序，没有内容的分类省略；
4. 分类标题统一使用三级标题，例如 `### 新增`；
5. 功能名称统一写成 `**功能名称**：内容`；
6. 不添加 `UPDATE_NOTES` 中不存在的功能，也不把开发过程中的临时修复补进历史公告；
7. 按文档站自身的构建流程确认页面和搜索索引生成成功；文档站工程不属于本仓库的前端构建依赖。

### 第五步：测试服验证

本开源包不包含顶层自动化测试目录。先完成构建和语法检查，再把候选脚本导入游戏测试服，逐项验证本次修改涉及的开关、正常流程、资源不足、重复事件、请求异常和边界条件。

涉及付费、消耗资源或自动提交的功能，必须验证预检、重复提交防护、服务端结果确认和停止条件。测试服验证失败时不得继续发布。

### 第六步：构建正式产物

```bash
npm run build
node --check "dist/奥术摸鱼大师辅助.user.js"
```

不得用手工复制或局部修改代替构建。

### 第七步：发布前校验

至少检查：

```bash
rg -n "@version|SCRIPT_VERSION" src/arcane-assistant-v2.1.3.base.js src/constants.js dist/奥术摸鱼大师辅助.user.js
rg -n "旧版本号" src dist package.json package-lock.json server/latest_version.txt
```

并人工确认：

- 构建产物包含最新公告和界面文字。
- 新功能默认开关符合预期。
- 旧设置升级后能够正常迁移或安全回退。
- 没有意外创建重复公告、临时文件或测试数据。
- 本地 `latest_version.txt` 更新不被误报成线上已发布。

## 五、线上发布流程

只有得到明确发布授权后执行本节。

### 1. 上传脚本

将正式产物上传并覆盖：

```text
/opt/asmy/arcane-assistant.user.js
```

上传后从公开下载地址读取文件，确认头部版本号、文件大小和关键公告内容正确：

```bash
curl -s https://reelax.hsiyue.com/arcane-assistant.user.js | head -20
```

### 2. 更新线上最新版本号

确认脚本已经上传成功后，再修改：

```text
/opt/asmy/latest_version.txt
```

顺序不能颠倒。若先更新最新版本号，旧版玩家会收到更新提示，但下载到的可能仍是旧脚本。

版本接口实时读取文件时通常不需要重启服务；是否重启以服务端实际实现为准。

### 3. 有服务端代码变更时

仅当 `server/main.go` 或其他服务端代码实际变化时：

```bash
cd server
go build -o collector .
```

上传新二进制、重启服务，并确认服务状态和接口正常。只有版本文本或脚本文件变化时，不应无意义重建服务端。

### 4. 数据结构变化

若 CSV、数据库或持久化结构发生变化，发布前必须制定迁移或备份方案。不得默认删除线上数据；删除旧数据必须获得明确授权并确认精确目标路径。

## 六、发布后验证

1. 从公开下载地址确认脚本头部为新版本。
2. 调用版本接口确认返回新版本号。
3. 使用旧版验证顶部更新提示能够出现并指向正确下载地址。
4. 使用新版验证更新说明首次加载弹出、刷新后不重复弹出。
5. 验证设置能够从旧版本保留，新功能采用约定的默认值。
6. 对本次新增的核心功能至少进行一次只读检查或安全场景验证。
7. 若涉及反馈、统计或服务端接口，确认线上请求和数据写入正常。

发布完成汇报必须区分：

- 本地测试与构建结果。
- 已上传的线上脚本版本。
- 线上版本接口返回值。
- 尚未完成或无法验证的项目。

## 七、发布检查清单

- [ ] 已确认上一个正式版本和本次比较基准。
- [ ] 公告只描述玩家可感知的最终差异。
- [ ] 公告未包含开发期间临时 bug 或内部实现流水账。
- [ ] 公告格式、顺序和语气与既有版本一致。
- [ ] `@version`、`SCRIPT_VERSION`、包版本和本地 `latest_version.txt` 一致。
- [ ] 必要的长期文档已同步，没有额外创建重复公告文件。
- [ ] 已在游戏测试服完成与改动范围相符的验证。
- [ ] `npm run build` 成功。
- [ ] 构建产物通过 `node --check`。
- [ ] 已核对构建产物版本号、公告、默认设置和关键界面文字。
- [ ] 线上发布已获得明确授权。
- [ ] 先上传新脚本，再更新线上最新版本号。
- [ ] 发布后已验证公开脚本、版本接口、更新提示和首次弹窗。

---

## 八、回滚流程

出现严重问题时按以下顺序处理：

1. 将线上 `latest_version.txt` 恢复为上一稳定版本，停止继续提示更新。
2. 用上一稳定产物覆盖线上 `arcane-assistant.user.js`。
3. 如涉及服务端，恢复上一稳定二进制并重启服务。
4. 验证公开下载地址和版本接口都已回到稳定版本。
5. 通知玩家关闭受影响功能或回退版本，并记录问题影响范围。
6. 修复完成后使用新的修订版本重新走完整发布流程，不直接覆盖同一版本号。

回滚不得使用不明确的通配符、递归删除或未经确认的数据清理命令。
